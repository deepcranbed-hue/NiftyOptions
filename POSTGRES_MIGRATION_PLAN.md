# Implementation Plan — PostgreSQL & TimescaleDB Migration

Consolidate NiftyOptions SQLite database files (`option_chains.db`, `snapshot_features.db`, `chain_store.db`) into a single PostgreSQL database with logical schemas. This plan focuses on a direct cutover using TimescaleDB for time-series optimization, Alembic for versioned schema management, connection pooling, and asynchronous pre-computation of analytical metrics.

---

## 1. Concrete System Alignment (Why & What)

### 1.1 The Real "Why" — Synced-File Locking Conflict
Our SQLite database files reside on a Google Drive synced directory. This sync process regularly locks database files during active writes, which forces us to run in `rollback-journal` mode (instead of WAL) with a high `30s` busy-timeout. 
* Moving to PostgreSQL entirely removes this synced-file contention since all clients query a PostgreSQL network service, decoupling disk sync locks from the application's transaction management.

### 1.2 Table & Storage Realities
* **No `option_chains` single table**: Option chain snapshots are stored across two tables inside `option_chains.db`:
  * `captures` (header metadata with `capture_id INT GENERATED BY DEFAULT AS IDENTITY`, `snapshot_minute`, `spot`, `status`, `trigger`).
  * `chain_rows` (individual option strike values with a foreign key to `capture_id`).
* **No Users or Sessions**: This is a single-process local backend running on `127.0.0.1`. We do not need multi-tenant schema-level roles or session management.
* **No Portfolio in SQLite**: The Strategy Desk portfolio resides in `.state/strategy_desk_portfolio.json`. The portfolio database migration is a non-issue.
* **Feature Store Rename**: `snapshot_features.db` is renamed to the more extensible `analytics.feature_values` to accommodate future live and training versions.

### 1.3 Sequencing Around the Hardening Plan
* This migration must be sequenced **after** the data architecture hardening plan (`DATA_ARCHITECTURE_HARDENING_PLAN.md`) is fully implemented.
* The hardening plan freezes analytical calculations. We must maintain byte-identical outputs during the PostgreSQL translation.
* `capture_id` will be defined as `GENERATED BY DEFAULT AS IDENTITY` to allow the one-time migration script to insert existing SQLite IDs while auto-generating keys for new rows.

## 2. Target Schema & TimescaleDB Layout

Instead of separate database files, we will use logical schemas within a single PostgreSQL database:

```
NiftyOptions DB
├── market/ (TimescaleDB hypertable optimized)
│   ├── captures (header metadata with GENERATED BY DEFAULT AS IDENTITY capture_id)
│   ├── chain_rows (hypertable chunked by captured_at)
│   └── price_bars (hypertable chunked by ts)
├── analytics/
│   └── feature_values (renamed from snapshot_features)
├── strategy/
│   └── instruments (lot size, strike steps, holiday sessions)
├── system/
│   ├── job_runs
│   └── worker_logs
└── news/
    └── articles
```

## 3. Work Breakdown & Timeline

### Week 1: Database Setup, Alembic & Data Migration
1. Deploy a PostgreSQL instance locally with the TimescaleDB extension.
2. Initialize Alembic within the workspace to track schema versioning.
3. Generate DDL migration versions to create schemas, tables, and indexes (testing the bulk migration script against a fully indexed database).
4. Write a one-time migration script (`scratch_scripts/migrate_sqlite_to_pg.py`) using `psycopg`'s copy protocols to transfer records from local SQLite files while preserving `capture_id` mappings.

### Week 2: Direct Store Rewrite & Deprecation
We will rewrite the query statements within the existing repository files directly to PostgreSQL syntax, bypassing long-term `sqlite3` driver imports:
* `chain_store.py` (chains, captures, and rows)
* `bar_store.py` (historical/live price bars)
* `features/store.py` (snapshot features)
* `signals/data_access.py` (quant signals)

For each store:
* Replace `sqlite3` connection instantiation with native connection borrowing from `psycopg.pool.ConnectionPool`.
* Rewrite SQL statements to use `%s` placeholders.
* Replace `INSERT OR IGNORE` / `INSERT OR REPLACE` with native `ON CONFLICT DO UPDATE` or `ON CONFLICT DO NOTHING`.
* Deprecate the SQLite code and local files.

### Week 3: Background Workers & Pre-computation Pipeline
* Set up worker processes under the `system` schema.
* Separate OLTP and Analytics workloads: calculate Greeks, PCR, and RND asynchronously when a capture completes or a new price bar is recorded, storing them in `analytics.feature_values` instead of on-demand calculations.
* Integrate Redis caching for dashboard reads.

### Week 4: Production Hardening
* **Backups**: Configure automated database backups and perform restore testing.
* **Monitoring**: Set up connection pool metrics and slow query logs.
* **Load & Failure Testing**: Validate system performance under concurrent calls and gracefully handle database disconnects.
